The open plan you are picking up (commit 1f848f4):

  "stream T3 tokens incrementally through the TTS resident to
  overlap T3 with S3Gen and eliminate GPU idle gaps."

  The user observed non-working GPU timelines during the realtime
  lecture synthesis: each chunk's T3 + S3Gen pass spikes the GPU,
  then the GPU goes idle while the Python side reads PCM and
  dispatches the next chunk. The log in
  data/lecture-realtime.log confirms the pattern with per-chunk
  speak_end -> speak_begin gaps.

  The fix: streaming T3 protocol. The resident accepts pieces
  incrementally over one socket. While S3Gen for piece N is on the
  GPU, T3 for piece N+1 starts. The wire protocol becomes
  {u32 piece_index, u32 path_len, u32 text_len, text, output_path}
  with a 0xFFFFFFFF sentinel to end. The session's
  pack_text_staged becomes piece-at-a-time, and
  session.synthesize_stream(text, sink, advance_callback) is the
  new entry point.

  Acceptance: the same 17-paragraph lecture must show GPU idle
  intervals between chunks near zero, total wall time reduced by
  30-50%, realtime streaming preserved, and cancel-on-interrupt
  still within the 60 ms PortAudio callback budget.

  STOP CONDITION: if chatterbox.cpp's Engine::synthesize remains a
  blocking single-call API, the implementer must not ship a partial
  overlap. The plan stops and the implementer reports the pin
  limitation with the artifacts collected.

The North Star (read this last, carry it as the goal of every
session; this is the human-language version of the lecture the user
spoke through v3 Polish at the end of this session, see
data/handover-lecture.txt for the spoken form):

  Trident is a place where a conversation with a machine has no
  artificial boundaries. There is no two-minute cap. There is no
  three-response cap. There is no boundary that says you can only
  speak when the machine has finished. Full duplex, not turn-taking.
  Real interrupt resilience, not pretended. Voice reproduction that
  sounds like you, or like anyone you choose, with no language limit
  and no length limit.

  Technically the north star is the tension between two poles. One
  pole is quality: fewer artifacts, more natural voice, shorter
  time to first audio. The other pole is responsiveness: less delay
  from the end of your sentence to the start of the machine's
  reply. The goal is the point where both are good enough that the
  user forgets they are talking to a machine.

  The lesson of this session, which is part of the north star: not
  every failure is a defect that needs a fix. Sometimes it is a
  mirage that disappears the moment you turn on the real hardware,
  write a real log, and look at the actual event times. Hypotheses
  that do not survive contact with artifacts should be discarded,
  not coded. Real hardware, real log, real times. Everything else
  is speculation.

  The four big themes for the sessions that follow, in order of
  leverage:

    1. Long-term memory. Today the conversation is stateless
       between sessions. The next session starts from zero. That
       is a large defect in the user experience, and that is the
       field to work in. Without it, the user has to re-establish
       context every time. With it, Trident becomes a partner
       rather than a tool.

    2. Streaming T3 (commit 1f848f4, in flight, gated on the
       chatterbox.cpp pin). The current wire protocol is
       request/response, so the GPU goes idle between chunks. A
       streaming T3 protocol closes the gap, makes the per-chunk
       wall time roughly max(T3, S3Gen) instead of T3 + S3Gen,
       and brings the time-to-first-audio from 3.5 s toward
       sub-second.

    3. Multimodality. Today the only channel is voice. Adding
       vision would open a different set of uses. This is a
       large topic, likely many sessions, and a VRAM question
       first (Gate 3 verdict must remain `ok`).

    4. Privacy and locality. Everything runs locally today, which
       is a strong property. The next step is to harden the
       boundary so that user data never leaves the machine. This
       is not a feature; it is a constraint on every future
       change.

  And the rule of every session, written so it is impossible to
  miss: every session begins by reading the diagnostic report,
  reading the latest plan, running the three Diagnostic Gates on
  the real rig, and only then thinking about new changes. This is
  not bureaucracy. It is the way to avoid the mistakes that
  already happened once. Real hardware, real log, real times.
  Everything else is speculation.
